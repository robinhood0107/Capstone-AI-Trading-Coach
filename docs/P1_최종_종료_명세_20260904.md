# P1 최종 종료 명세 — 실제 DB 시연판

기준일: 2026-09-05
대상: 단일 사용자 KIS 모의투자 시연
제품 원칙: 데이터가 없으면 없다고 말하고, 수익을 보장하지 않으며, 주문 전 안전장치를 우회하지 않는다.

## 1. 최종 목표

금융 지식이 많지 않은 사용자가 다음 흐름을 한 서비스 안에서 수행한다.

1. 자동운용 상태와 KIS 모의투자 계좌를 확인한다.
2. 금융 Agent에서 개념과 위험을 출처와 함께 질문한다.
3. 자신의 손실 제한·종목 비중·주문 한도를 원칙으로 저장한다.
4. 동일한 실제 DB 입력으로 Baseline, Guide, Strict 결과를 비교한다.
5. 자동운용이 만든 최신 주문 판정과 이유를 확인한다.
6. 배운 내용과 판단을 학습일지에 남긴다.

자동운용의 사용자 의도는 항상 ON이다. 정상적으로 한 번 arm된 뒤에는 다음 XKRX 세션 예약을 유지한다. 일반 사용자 화면에는 중지 버튼이 없다. 다만 Kill Switch, 운영자 중지, 인증·잔고·시장데이터·대사 오류는 계속 HALTED 또는 DISARMED를 만들 수 있으며, 화면은 이를 “작동 중”으로 바꾸어 말하지 않는다.

| 금융 Agent | RAG v2 corpus·동의·ask·history, RAG source registry | 전체 답변, 인용, 최근 질문, 등록 출처 |

## 3. 실제 시나리오 재생

### 3.1 입력과 규칙

`owner-scenario-replay.v1`은 외부 provider를 호출하지 않고 현재 DB와 검증된 Team B bundle만 읽는다.

- 모델 입력 기간: 2026-04-03~2026-09-03, XKRX 104세션
- 운영 평가 기간: 2026-08-18~2026-09-03, XKRX 13세션
- universe: exact-31
- OHLCV: 3,224행
- 초기자본: 10,000,000원
- 배분: 종목별 균등 예산, long-only
- 비용: 왕복 35bp
- Baseline: production `trend_only` RULE_BASELINE
- Guide: RULE BUY이고 LSTM이 SELL이 아닌 후보를 허용하는 `rule_lstm_veto`
- Strict: Guide 후보에 저장된 Principle과 결정적 RiskEngine 한도를 적용

프로그램 기동일은 2026-08-17이다. 이날은 XKRX 대체공휴일이므로 첫 운영 거래일은 8월 18일이다. 8월 17일 이전 OHLCV는 LSTM 20개 feature row와 이동평균을 만드는 warm-up 입력으로만 사용하며 운영 이력과 화면 곡선에는 노출하지 않는다. 각 거래일 신호는 직전 거래일까지의 데이터로 계산하고 해당 거래일 종가로 체결·평가한다. 화면 시각은 종가 의미에 맞춰 15:30 KST로 표시한다.

입력 bar, model bundle, Principle, 비용을 canonical JSON으로 묶어 run identity를 만든다. 같은 입력을 재실행하면 같은 run과 projection hash가 나오며 기존 행을 바꾸지 않는다. 결과에는 `performanceClaimAllowed=false`가 들어간다.

## 4. KIS Mock 자동운용 증거

KIS 모의계좌의 현재 잔고, 주문 식별자, 보유수량과 체결가는 설치별 로컬 DB와 owner-only runtime에만 둔다. Git 문서에는 특정 계좌의 실행 ID, 종목별 보유수량, 체결가를 기록하지 않는다.

history replay는 별도 INTERNAL_PAPER 계좌에 기록되며 KIS 상태·포지션·실현손익 집계에서 제외된다. Team A acceptance seed는 KIS run 또는 실제 포지션이 있는 DB를 발견하면 삭제 전에 실패한다. 따라서 신규 clone은 공통 schema와 provider-free fixture만 받고, 사용자가 연결한 KIS Mock 계좌의 관측과 자동매매 포지션은 그 설치의 로컬 DB에서만 생성된다.

자동운용 활성화의 마지막 조건은 `./capstone mock readiness`의 PASS다. FAIL이면 arm하지 않는다. KIS Live order와 GDELT outbound는 0이다.

## 5. 금융 Agent

금융 Agent는 메뉴 두 번째와 홈의 주요 진입점에 배치한다. 답변은 요약으로 잘라내지 않고 저장된 전체 문장을 표시한다. 동의, 질문, 답변, 근거, 최근 질문, 등록 출처를 한 화면에서 탐색한다.

현재 source registry는 DB에 등록된 공개 `PROJECT_SOURCE_CARD`와 `UPSTREAM_REFERENCE`를 읽는다. 데모 DB의 등록 출처는 20개다. source ID는 React key와 조회용으로만 사용하고 화면에 노출하지 않는다.

RAG는 금융 지식 설명 기능이다. Signal, RiskDecision, 주문 수량, 주문 제출 권한은 0이다. 매수·매도 조언과 계좌 개인정보 질문은 guardrail에서 차단한다.

## 6. 로그인과 비밀 관리

로그인은 유지하고 회원가입, 이메일 복구, 첫 로그인 challenge는 만들지 않는다. 설치 시 demo user/admin의 고엔트로피 임시 비밀번호를 발급하고 BCrypt cost 12, 로그인 제한, `securityVersion` 기반 세션 무효화를 재사용한다.

비밀번호 정책은 15~64자, 로컬 blocklist에 있는 흔한·유출 비밀번호와 서비스명·username 포함 금지다. 조합 규칙과 정기 강제 변경은 없다. `./capstone credential rotate user /absolute/password-file`은 DB credential, bundle, password file과 자동운용의 owner password를 함께 바꾸고 기존 세션을 무효화한다.

loopback 시연판은 access token을 탭 단위 `sessionStorage`에 둔다. 탭을 닫으면 사라지지만 JavaScript에서 읽을 수 있으므로 인터넷 공개형 다중 사용자 인증으로 보지 않는다. 비밀 원문은 Git, image, 로그, UI, 문서에 넣지 않는다.

## 7. 구성과 재현

```text
Browser
  -> Next.js Experience Dashboard
  -> Kotlin/Spring Decision Platform
      -> PostgreSQL: 사용자, 원칙, 판정, 자동운용, RAG history, dashboard projection
      -> Redis: 짧은 수명의 런타임 상태
      -> Python workers: Return inference, RAG, KIS adapter, scenario materializer
      -> KIS Mock: 승인된 경우에만 모의 계좌 read/order
```

신규 clone의 기본 순서는 다음과 같다.

```bash
git pull
./capstone doctor
./capstone up
./capstone status
```

`doctor`가 만드는 `.state-app/secrets`와 demo password 파일은 Git에 포함되지 않는다. `up`은 V1부터 최신 Flyway migration을 적용하고 공개 RAG seed, identity, Team B artifact, 시장데이터, history replay, 실제 시나리오 projection을 멱등하게 준비한다. 로그인 암호는 화면이나 로그가 아니라 owner-only password 파일에서 확인한다.

KIS Mock 자동운용은 `mock configure`, 거래시간의 `mock certify`, `up --mock`, `mock gate-author`, `mock readiness`, `mock start` 순서로 별도 활성화한다. 인증 전 `up --mock`을 성공 경로로 설명하지 않는다.

## 8. 역할 분담

| 담당 | 최종 책임 | 통합 경계 |
|---|---|---|
| 박종진 / Decision Platform | Spring API, Principle/Risk/RAG, 금융공학, KIS Mock 자동운용, DB·보안·배포 통합 | 검증된 model/backtest artifact를 읽고 최종 주문 판단과 설명을 저장 |
| Team B / Return Engine | RULE_BASELINE, LSTM, 동일 조건 backtest 원천 | exact-10 bundle과 manifest 제공; Owner는 원본 bytes를 수정하지 않음 |
| Team A / Experience Dashboard | 사용자 흐름, 모델 평가, 리포트 표현 | same-origin API 계약을 소비하고 내부 ID·결측 대체값을 숨김 |

최종 통합 과정에서 Owner가 Dashboard의 실제 API wiring과 provider-0 materialization을 보강했지만 원천 모델 소유권은 바꾸지 않는다. LightGBM 연구 코드는 보존하되 제품 UI, 현재 소개, 시연, 활성 P1 의존성에서는 제외한다.

## 9. 검증 등급

| 등급 | 뜻 |
|---|---|
| IMPLEMENTED | 코드와 migration이 존재함 |
| LOCAL_TESTED | 관련 단위·계약·통합 테스트가 통과함 |
| COMPOSE_VERIFIED | 실제 Compose와 DB에서 재현됨 |
| PROVIDER_VERIFIED | 허용된 외부 provider 호출 결과가 저장·화면까지 이어짐 |
| MERGED | PR CI 성공 후 main merge SHA가 존재함 |

건강한 컨테이너나 smoke PASS만으로 자동매매 readiness, provider 검증, merge를 대신 주장하지 않는다. 최종 인수표는 실제 실행 직후 이 문서와 PR에 동일하게 기록한다.

`CODEX_SECURITY_DEEP_SCAN=NOT_RUN_USER_SCOPED_OUT`. 기존 P1 보안 게이트만 실행하며 이를 별도 보안 종결로 표현하지 않는다.

## 10. 저장소와 작업 이력 조사

최종 문서는 tracked Markdown 273개, 로컬 참고 Markdown 174개, Git commit 1,871개, merged PR 157개를 제목·역할·결정·검증 기준으로 인덱싱해 작성했다. Codex 로컬 SQLite의 `local_thread_catalog`에서는 이 저장소 cwd와 정확히 일치하는 작업 101개를 확인했다. 관측 기간은 2026-07-06~2026-08-26이며 원문 prompt, 비밀번호, API key, 계좌번호와 개인 파일 내용은 복사하지 않았다.

코드와 테스트 주석은 first-party Python, Kotlin, TypeScript, shell을 대상으로 감사했다. 변경 일지, 장애 당시 서술, 코드의 단순 재진술은 제거하고 보안 경계, 멱등성, 계산식과 비표준 선택의 이유만 짧게 남겼다. 생성물, 동결 계약과 보존 연구 worktree는 수정하지 않았다.
