# S0.2 P0 계약 통합 필드명 결정

이 문서는 S0.2에서 추가한 P0 contracts schema를 기준으로, API 명세서와 최종 프로젝트 명세서 사이에 표현 차이가 있던 필드명을 통합 기준으로 고정한다. 이 결정은 `contracts/schemas/*.schema.json`과 `contracts/examples/*.json`의 기준이며, 이후 변경은 `contracts/changes/`에 기록하고 schema validation을 함께 갱신한다.

모델 위험·근거 의미 검토일: 2026-07-17

## 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 주문 가격 필드 | canonical이자 유일한 지원 필드는 `estimatedPrice`다. `price` alias는 지원하지 않는다. | 주문 전 평가 payload라는 의미를 명확히 하고 구현되지 않은 alias가 계약에 남는 것을 막는다. |
| Signal artifact 단위 | artifact 저장/교환은 row 단위 signal record를 기준으로 하고, Signal API 응답은 Spring이 row를 조합한 view payload로 제공한다. | 최종 명세서 6.4/6.5는 `lstm_signals.parquet`, `rule_baseline_signals.parquet`, `lightgbm_signal.json` 교환을 전제하고, API 8.1은 화면 조회용 component 묶음을 제공한다. |
| HMM regime enum | P0 wire compatibility superset은 `NORMAL`, `SIDEWAYS`, `HIGH_VOLATILITY`, `RISK_OFF`, `RISK_ON`을 유지한다. S6.1 active 2-state HMM producer가 새로 생성하는 native state는 `RISK_ON`, `RISK_OFF`뿐이다. | 기존 schema/example을 깨지 않으면서 모델 state 수와 wire vocabulary를 혼동하지 않는다. |
| 모델 `confidence` | `0..1` wire 범위만 공통이고 producer별 의미는 동일하지 않다. LightGBM은 시간순 OOS calibration을 통과한 확률만 `confidence`다. | raw score, HMM posterior, 캘린더 source confidence를 하나의 확률 의미로 오해하지 않게 한다. |
| Return Engine parquet 컬럼명 | Decision Platform ingest용 컬럼명은 schema 필드명과 camelCase를 맞춘다. Parquet 내부 구현 컬럼이 다르면 export 단계에서 변환한다. | `contracts/`를 workspace 간 단일 진실 소스로 두는 최종 명세서 6.3/6.4 원칙에 따른다. |

## Order Intent 필드명

Decision API의 order intent는 주문 제출 전 평가 요청이므로 실제 체결가가 아니라 주문 후보의 예상 가격을 담는다. 따라서 `estimatedPrice`를 표준 필드로 사용한다.

S0.2 이후 schema, API 문서, OpenAPI, adapter와 새 예시는 `estimatedPrice`만 허용한다. `price`는 구현된 호환 계약이 아니므로 deprecated alias로도 추가하지 않는다. 기존 문서나 fixture에서 발견되면 `estimatedPrice`로 교정하고 contract validation으로 회귀를 막는다.

## Signal artifact와 API view

Signal 계약은 두 형태를 구분한다.

| 형태 | 용도 | 기준 |
|---|---|---|
| Artifact row | Return Engine/Decision Platform이 파일로 export하고 Spring이 ingest하는 단위 | `symbol`, `producer`, `sourceWorkspace`, `asOf`, `timeframe`, `signal`, `confidence`, `predictedReturn`, `featureSummary` |
| API view | Dashboard가 `/api/v1/signals/{symbol}`로 조회하는 화면용 묶음 | `ruleBaseline`, `lstm`, `lightgbm`, `newsSentiment`, `hmmRegime` component를 포함 |

`contracts/schemas/signal.schema.json`은 S0.2에서 API view payload를 검증할 수 있도록 component 묶음을 포함한다. Return Engine이 parquet로 내보내는 `lstm_signals.parquet`, `rule_baseline_signals.parquet`는 row 단위 필드를 사용하고, Spring ingest/aggregation 단계에서 API view 형태로 조합한다.

`producer`와 `sourceWorkspace`는 다음처럼 고정한다.

| producer | sourceWorkspace |
|---|---|
| `RULE_BASELINE` | `return-engine` |
| `LSTM` | `return-engine` |
| `LIGHTGBM` | `decision-platform` |
| `COMPOSITE` | `decision-platform` |

`COMPOSITE`는 Spring API가 여러 모델 신호와 리스크 보조 정보를 조합한 조회 payload임을 나타낸다. 원천 모델 artifact에는 `COMPOSITE`를 쓰지 않는다.

`COMPOSITE`는 독립 학습모델이나 새 확률분포가 아니다. 여러 component를 화면에 묶은 view이며
component confidence를 평균해 새로운 “정확도”로 만들지 않는다. `predictedReturn`도 지정 horizon의
point estimate일 뿐 보장 수익률이나 주문 권한이 아니다.

## HMM regime enum

HMM은 가격 예측 모델이 아니라 시장국면의 잠재 통계 label을 추정하는 WARN-only 보조 필터다.
P0 schema의 5개 값은 기존 API 예시와 fixture를 수용하는 **wire compatibility superset**이다.
이는 HMM을 5-state로 학습한다는 뜻이 아니다.

| 값 | P0 wire 상태 | S6.1 active producer 규칙 |
|---|---|---|
| `NORMAL` | 기존 예시/fixture 호환을 위해 허용 | native HMM state로 새로 생성하지 않음 |
| `SIDEWAYS` | 기존 예시/fixture 호환을 위해 허용 | native HMM state로 새로 생성하지 않음 |
| `HIGH_VOLATILITY` | 기존 예시와 deterministic/composite risk 표시 호환 | native HMM state가 아님. rolling volatility rule과 별도 필드/근거로 계산 |
| `RISK_OFF` | 허용 | active 2-state HMM의 상대적으로 높은 risk-score component label |
| `RISK_ON` | 허용 | active 2-state HMM의 상대적으로 낮은 risk-score component label |

S6.1은 `n_components=2`로 고정하고 운영 시점 `t`의 posterior를
`P(z_t | x_1..x_t)` direct forward recursion으로 계산한다. 전체 sequence의
Viterbi/MAP/forward-backward smoothing 결과를 운영 feature로 사용하지 않는다. 미래 suffix가
달라져도 과거 prefix posterior가 바뀌지 않아야 한다.

`hmmRegime.probability`는 causal filtered posterior이지 실제 시장 원인의 확률이나 물리적
방향확률이 아니다. v1 운영 gate는 `maxPosterior >= 0.65`이고 normalized entropy는
posterior가 거의 균등한지를 보여 주는 secondary diagnostic이다.
`hmm-regime-policy-v1`에서는 normalized entropy가 exact `> 0.95`일 때만
`HIGH_POSTERIOR_ENTROPY` warning이고 equality는 warning이 아니다. 운영 gate를 통과하지
못하면 내부 결과는 `ABSTAIN`이고 state를 위조하지 않는다.

현재 P0 success wire는 `hmmRegime.state/probability`를 필수로 요구하면서 `ABSTAIN` enum과
component별 provenance/staleness를 표현하지 못한다. 따라서 구현은 다음 안전 bridge를 따른다.

1. HMM 내부 결과는 `ABSTAIN`으로 종료하고 새 state/probability를 만들지 않는다.
2. 이전 valid view가 있더라도 원래 `asOf`를 바꾸지 않으며 fresh model evidence나 주문 입력으로
   재사용하지 않는다.
3. `NORMAL`, `HIGH_VOLATILITY`, 임의 probability, `confidence=0.0`을 ABSTAIN 대용으로
   꾸며 내보내지 않는다.
4. 현재 required Signal/RiskDecision success wire를 구성할 수 없으므로 API 경계에서는 기존
   `SignalService`/schema failure mapping인 `PYTHON_SERVICE_UNAVAILABLE → HOLD`를 따른다.
5. 이 HOLD는 HMM posterior가 경제적으로 주문을 차단한 결과가 아니라 필수 교환 계약을 만들 수
   없는 service/schema-availability 실패다. 내부 deterministic hard guard 계산을 별도로
   수행했더라도 불완전 success payload로 바꾸어 반환하지 않는다.

ABSTAIN과 component provenance를 success payload에 직접 노출하려면 별도
`contracts/changes/`에서 Signal/RiskDecision schema, examples, API failure mapping을 함께
변경한다. 그 전까지 S5.5/S6.1의 HMM active wire integration은 `NO-GO`이고 offline causal
kernel·fixture 검증만 진행할 수 있다.

Dashboard 표시는 한국어 라벨로 바꿀 수 있지만 latent state를 인과적 시장 실체로 설명하지
않는다. HMM posterior 하나로 `ALLOW`, `HOLD`, `BLOCK` 또는 계약수를 결정하지 않는다.

## 모델 confidence 의미와 권한

`confidence`는 숫자 범위만 공통이다. producer·artifact별 의미와 검증 근거가 다르므로 서로
직접 비교하거나 평균하지 않는다.

| 값 | 허용 의미 | 실패 시 처리 |
|---|---|---|
| Rule baseline `confidence` | deterministic rule score. 물리확률 아님 | rule provenance 누락 시 component 무효 |
| LSTM `confidence` | 팀원 B가 별도 계약·OOS 검증으로 정의한 model score/probability | 정의·검증 근거 없으면 주문 권한 없음 |
| LightGBM `confidence` | 시간순 validation-only Platt/isotonic calibration과 untouched OOS 평가를 통과한 확률 | calibration FAIL/drift이면 기존 artifact의 `signal=HOLD`, `confidence=0.0`은 모델 abstention label일 뿐 RiskEngine HOLD가 아님; raw `modelScore`는 public artifact/API 비노출 |
| HMM `probability` | `P(z_t | x_1..x_t)` causal posterior | 내부 low max posterior/stale은 ABSTAIN, high entropy는 diagnostic WARN. 현재 required success wire를 만들 수 없으면 임의 state 없이 기존 service failure `HOLD` |
| 캘린더/event `confidence` | source reliability·독립 일치·충돌 상태 | 투자 확률이나 모델 score로 사용 금지 |

모든 signal과 model probability는 주문 후보·설명 입력이며 주문 권한이 없다. 실제
`ALLOW/WARN/HOLD/BLOCK`은 fresh 가격·잔고·원칙·손실한도·margin 같은 deterministic
RiskEngine 근거와 별도 validation을 거친다.

## Return Engine export 컬럼명

팀원 B가 담당하는 `lstm_signals.parquet`, `rule_baseline_signals.parquet`는 Decision Platform ingest 경계에서 아래 이름을 제공해야 한다.

| 컬럼 | 타입 기준 | 설명 |
|---|---|---|
| `symbol` | string | 종목 코드 |
| `producer` | enum | `LSTM` 또는 `RULE_BASELINE` |
| `sourceWorkspace` | enum | 항상 `return-engine` |
| `asOf` | ISO-8601 string | 신호 기준 시각 |
| `timeframe` | enum | `1d` 또는 `60m` |
| `signal` | enum | `BUY`, `SELL`, `HOLD` |
| `confidence` | number | 0 이상 1 이하. producer별 정의·OOS/calibration 근거가 필요하며 producer 간 직접 비교·평균 금지 |
| `predictedReturn` | number 또는 null | 예측 수익률. 산출 불가 시 null |
| `featureSummary` | string array | 신호 근거 feature 요약 |

Parquet 내부 컬럼이 snake_case여도 무방하지만, artifact export 또는 ingest adapter에서 위 계약명으로 변환해야 한다. Spring, Dashboard, 계약 예시는 camelCase 필드명을 기준으로 한다.

## 교육 자료와 계약 근거의 분리

옵션·랜덤 워크·BSM·HMM·diffusion을 연결한 교육 영상/학습 Markdown은 개념 이해와 source
discovery에 사용할 수 있지만, 이 P0 field 의미를 직접 바꾸지 않는다. 모델 score를 확률로
승격하거나 HMM label을 실제 원인으로 해석하는 근거로 사용할 수 없으며, 수식·수치·특정 사건은
primary research 또는 공식 보고서와 명시적인 contract change로만 채택한다.

특히 다음 값은 같은 “위험 숫자”로 합치지 않는다.

| 값 | 계약 의미 |
|---|---|
| option premium | 권리를 사거나 의무를 부담하기 위해 지급/수취한 가격 |
| contract notional | 계약 지급액 계산의 기준 규모 |
| valuation delta-equivalent exposure | BSM 등 특정 estimator의 국소적인 기초자산 1차 민감도 환산. model evidence이며 hard 주문한도 단독 근거가 아님 |
| conservative delta-equivalent exposure | P2 hard guard용 계약상 보수 경계. KOSPI200 option v1은 call `+1`, put `-1`의 `conservativeRiskDelta`와 공식 contract source hash를 사용 |
| margin | broker/clearing의 담보·주문가능 요건 |
| deterministic stress loss | 명시한 충격에서의 조건부 손실이며 최대손실·발생확률이 아님 |
| gross market value | 계약의 양(+)·음(-) replacement-value 성격 시장가치 총액. notional·credit exposure와 별개 |
| gross credit exposure | 법적으로 유효한 bilateral netting 뒤의 gross market value 기반 신용노출. 담보 반영 여부는 각 공식 source definition을 함께 기록 |

파생 확장 schema에서 이 값들을 노출하려면 이름·단위·`asOf`·source를 각각 가진 별도 필드로
정의하고 `contracts/changes/`를 동반한다. 프로젝트 주문 snapshot의
`grossCurrentMarketValue`와 BIS 집계의 `grossCreditExposure`는 목적·범위·netting 단위가
다르므로 같은 필드나 값으로 혼용하지 않는다.

기대 payoff도 `measure`, discounting, horizon, estimator/model을 함께 기록한다. 실제분포
`P`의 예측 기대값과 위험중립 `Q`의 무차익 가격은 같은 값이 아니며 어느 쪽도 단일 경로의
보장값이 아니다. 수치 커널이 순수하고 재현 가능하다는 사실은 표본·calibration·OOS 같은
통계적 유효성이나 비용·유동성·레버리지·시장충격 같은 경제/운영 유효성을 자동으로
증명하지 않는다.

교육 자료에서 금융가격의 Brownian/GBM diffusion과 AI DDPM을 비유할 수는 있지만, DDPM은
학습된 reverse denoising process를 포함하는 별도 모델이다. 두 모델의 수식·fixture·API를
서로 교환하지 않는다.

## Artifact manifest 해시 기준

`artifact_manifest.json`의 `files[].sha256`은 `sha256:<hash>`가 아니라 64자리 hex digest만 기록한다. API 2A의 `fileHash`처럼 접두사가 필요한 내부 상태 API와 구분한다.

예:

```json
{
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```
