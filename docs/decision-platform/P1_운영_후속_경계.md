# 자동매매와 운영 경계

## 결론

V90 persistent runtime, `./capstone mock readiness|start|stop`, XKRX boundary loop와 transient next-session scheduler가 구현됐습니다. 기본값은 계속 mock OFF, automation OFF이며 current local runtime은 activation gate 0, ARMED 0입니다. 실제 Team B artifact와 KIS Mock certification이 없으므로 자동 모의투자는 여전히 NO-GO입니다.

```text
AUTOMATION_CONTROL_API=IMPLEMENTED_EXACT_4
AUTOMATION_PERSISTENT_RUNTIME=IMPLEMENTED_INACTIVE
AUTOMATION_RUNTIME_ROLE=decision_automation_runtime
MOCK_READINESS_START_STOP=IMPLEMENTED_FAIL_CLOSED
NEXT_SESSION_SCHEDULER=IMPLEMENTED_TRANSIENT_SYSTEMD
VERTEX_BUY_VETO_PRODUCTION_TRANSPORT=ABSTAIN_NOT_CONFIGURED
RECURRING_AUTOMATION=DISABLED
KIS_MOCK_CERTIFICATION=NOT_RUN
KIS_LIVE_CALLS=0
```

## 구현된 Owner runtime

- V90 owner/session 단일 claim, durable checkpoint, processed tick identity, sanitized reservation, submit count 최대 1
- orderId와 one-way provider reference hash 결속, activation-gate authoring, append-only event, restart-safe CAS
- Python `AutomationEngine`과 Spring Decision/Risk/Kill Switch/Brokerage, KIS quote/buyable/execution/cancel adapter 연결
- 09:10 신규 판단, 09:20 이후 신규 주문 0, 15:20 cancel/reconcile, 다음 XKRX boundary까지 대기
- default DISARMED, quantity 1, LIMIT, KRX-only, no-margin, write retry 0
- SELL Vertex call 0, VETO/ABSTAIN order 0, second candidate·fallback·reorder·물타기·강제청산 0
- disarm 뒤 신규 주문만 중단하고 active reconciliation과 durable volume 보존

production Vertex grounding transport는 아직 주입되지 않아 신규 BUY가 `ABSTAIN`으로 닫힙니다. fixture 검증은 통과하지만 이 상태를 실제 closed-loop KIS Mock E2E로 주장하지 않습니다.

## CLI와 다음 session 예약

```bash
./capstone mock readiness
./capstone mock start
./capstone mock stop

python scripts/p1_mock_next_session.py
python scripts/p1_mock_next_session.py --execute
```

readiness는 credential configured, certification, clean release/source binding, REAL_TEAM_B pointer·integrity receipt, Kill Switch, account baseline, unresolved drift/order, control version과 next XKRX session의 content-free marker만 출력합니다. start는 전 gate PASS일 때 다음 session을 ARMED하고 runtime을 켜지만 즉시 주문하지 않습니다. stop은 신규 주문만 DISARM합니다.

예약 스크립트는 기본 dry-run입니다. `--execute`일 때만 `systemd-run --user --collect --on-calendar` transient unit을 다음 XKRX session 08:55 KST에 한 번 만들고 owner-only `0600` canonical receipt를 남깁니다. cron, persistent timer, nohup, infinite sleep과 retry는 없습니다. 08:55에는 readiness와 start만 실행하며 provider/account/order 호출은 0입니다.

## 실제 activation 전에 필요한 외부 gate

1. actual REAL_TEAM_B exact-10/pointer와 Owner integrity receipt
2. actual Team A production UI
3. KIS Mock credential과 별도 exact physical certification 승인
4. certification PASS, clean merged release/source binding
5. production Vertex BUY-veto grounding transport와 budget/credential gate
6. 연속 3개 pinned XKRX session soak와 security/supply-chain release gate

certification 당일 전략 주문은 0이며 `strategyEligibleFromSession`은 그 다음 pinned XKRX session입니다. 위 조건 전 synthetic/preview를 주문 근거로 승격하지 않습니다.

## 일반 자동매매 봇과 비교한 부족분과 1.2.0 제안

1.1.0에서 폐루프 자체는 닫혔습니다. 신호에서 주문, 체결, 포지션, 실현손익까지 이어지고 매 tick이
durable하게 남습니다. 그래도 흔한 리테일 자동매매 봇이 갖춘 것 중 아직 없는 게 있습니다. 의도적으로
비워 둔 것과 그냥 안 만든 것을 나눠 적습니다.

### 의도적으로 비워 둔 것 (1.2.0에서도 유지)

강제청산, 물타기, second candidate, 실계좌 주문 경로. 교육용 경계라 넣지 않습니다.

P0 둘은 지금 구조에 얹기 쉽습니다. 실현손익은 이미 저장되고 있어 조회만 붙이면 되고, 알림은
`automation_events`의 `DRIFT_DETECTED`를 그대로 쓰면 됩니다.

P1의 자동 서킷브레이커는 `DAILY_LOSS_RATE`와 `MDD`가 이미 hard readiness metric으로 계산되고 있어
임계 비교만 추가하면 됩니다. 다만 자동으로 꺼지는 동작이라 사용자 확인 없이 넣지 않는 편이 좋겠습니다.

P2 셋은 1.2.0 범위에서 결정할 문제입니다. 특히 노출 한도는 `openPositionMarketValueKrw`가 지금 상수
`0`이고 원칙 자산 한도가 `MAX_BIGINT`로 들어가 있어, 수량 산정이 사실상 예산과 매수가능금액만 보고
있습니다. 실제 보유 평가액을 넣는 것이 먼저입니다.

## 뉴스 거부권 grounding을 등록 코퍼스로 옮긴 이유

`vertex-news-veto.v1`은 근거마다 **host가 독립적으로 아는 발행일**을 요구한다. 모델이 보고한
`sourceEventDate`가 host 관측값과 일치해야 통과한다. 그런데 Vertex + Google Search grounding
metadata는 URI, 제목, 지지 문장만 주고 발행일을 주지 않는다. 즉 웹검색 grounding으로는 이 계약을
만족시킬 방법이 없다.

세 선택지 중 등록 코퍼스 grounding을 택했다. 이미 수집·색인한 문서만 근거로 쓰면 host가 인용문과
발행일을 정확히 안다. 대신 "Google 질의 수"라는 신뢰 신호가 의미를 잃으므로 계약을 그만큼 완화했다.

| 바뀐 것 | 전 | 후 |
|---|---|---|
| 응답 필드 | `googleGroundingQueryCount` 1로 고정 | `groundingMode=REGISTERED_CORPUS`, `groundingQueryCount` 1~8 |
| grounding 출처 | Google 웹검색 결과 | 요청 패킷의 `publicEvidence` |
| 출처 유형 판정 | 모델 주장 | `contracts/catalogs/p1-vertex-news-sources.v1.json` 대조 |

구현은 셋으로 나뉜다. `app/p1_owner/vertex_source_registry.py`가 URI를 등록 출처로 판정하고,
`app/p1_owner/vertex_corpus_evidence.py`가 신선도·인용 경계를 강제해 `publicEvidence`를 만들고,
`app/p1_owner/vertex_transport.py`가 tool 없이 generateContent 한 번만 호출한다. `vertex_veto.py`의
검증 순서와 ABSTAIN 사유는 건드리지 않았다.

fail-closed는 그대로다. 설정이 없으면 기존 fail-closed transport가 쓰이고, 근거가 0개면 provider를
아예 부르지 않으며, 인증·시간초과·형식오류·세션 호출 상한 초과는 모두 기존 ABSTAIN 사유로 닫힌다.

### 아직 남은 것

**회사 뉴스 코퍼스가 없다.** GDELT 경계는 집계 tone·volume만 주고 기사 본문과 발행일을 주지 않아
인용 근거가 되지 못하고, RAG 코퍼스는 금융 개념 카드라 종목 뉴스가 아니다. 따라서 지금
`publicEvidence`는 항상 비어 있고 거부권은 항상 `ABSTAIN`이다. 실운용에는 두 가지가 더 필요하다.

1. 날짜와 본문을 가진 종목 뉴스 수집 경로 (`CorpusDocumentSource` 구현)
2. Vertex credential — `VERTEX_PROJECT_ID`, `VERTEX_LOCATION`, `VERTEX_SERVICE_ACCOUNT_FILE`.
   셋이 모두 있을 때만 실 transport가 선택된다. 하나라도 없으면 기존 fail-closed다.
