# 자동매매와 운영 경계

## 결론

현재 앱은 24시간 켜 둘 수 있지만 **자동 주문 프로그램은 아닙니다**. 켜 둔 것만으로 시세·계좌를
조회하거나 주문하지 않습니다. 최종 프로젝트 목적에는 자동 모의투자가 포함되므로 주문 스케줄러는
나중에 구현해야 하지만, “24시간 거래”가 아니라 “24시간 서비스 + 한국거래소 session 안의 제한된
모의주문” 구조가 맞습니다.

| 항목 | 현재 상태 | 판정 |
|---|---|---|
| 앱·DB·Dashboard 24시간 실행 | 가능 | 현재 목적에 맞음 |
| 내부 작업 큐·지표·RAG 정리 | 구현됨 | 주문과 무관한 운영 작업 |
| 프로그램 시작 시 자동 주문 | 없음 | 안전한 현재 상태 |
| 거래시간 자동 모의주문 | 없음 | 최종 목적에는 필요하지만 지금 구현하면 안 됨 |
| KIS 모의주문 수동 인증 | 코드 있음, 아직 실행 안 함 | 다음 거래시간에 Owner가 한 번 검증 |
| KIS 실계좌 주문 | 차단됨 | 계속 구현·활성화하지 않음 |

## 실제로 예약 실행되는 코드

Spring의 예약 작업은 세 종류뿐입니다.

1. 5초마다 내부 DB 작업 큐를 확인합니다. 처리 종류는 RAG 색인, 결과 파일 적재, 모델 평가입니다.
2. 1분 또는 5분마다 판단 분포, 실패 작업, 신호 신선도와 DLQ 지표를 집계합니다.
3. 1시간마다 만료된 RAG 이력을 정리합니다.

주문 이벤트를 만드는 cron, Quartz job, systemd timer 또는 Python scheduler는 없습니다. 주문 API는
인증된 사용자의 HTTP 요청이 들어왔을 때만 실행되고, `--mock` 모드의 Python 서버도 RPC 요청을 기다릴
뿐 스스로 주문하지 않습니다. Team A 현재 화면에는 주문 제출·취소 흐름도 아직 없습니다.

## 왜 지금 자동 주문을 구현하면 안 되는가

1. 현재 Team B 결과는 받은 CSV/PTH 미리보기이고 실제 모델 결과가 아닙니다.
2. Team B 결과를 Signal/모델 평가/백테스트 API에 적재하는 production adapter가 없습니다.
3. Team A의 주문 전 판정, KIS 모의주문, 주문 조회·취소 화면이 완성되지 않았습니다.
4. KIS 모의투자 수동 인증을 실제 거래시간에 통과하지 않았습니다.
5. 자동매매 활성 상태, 전략, 거래 창, 일일 상한과 실행 이력을 저장할 API가 OpenAPI에 없습니다.

이 상태에서 scheduler를 붙이면 미리보기나 synthetic 데이터를 실제 모의계좌 주문의 근거로 사용할 수
있습니다. 따라서 지금은 주문 scheduler를 추가하지 않는 것이 프로그램 목적과 안전 요구에 맞습니다.

## 나중에 구현할 올바른 구조

### 24시간 동작할 부분

- 서비스 health와 컨테이너 복구
- DB 작업 큐와 결과 파일 적재
- 신호 신선도와 실패 작업 감시
- 미확정 주문 대사와 알림
- 다음 XKRX session 계산

### 거래 session에만 동작할 부분

- 고정된 XKRX calendar로 거래일 확인
- 장 시작 직후의 안전 여유와 장 마감 전 중단 시간을 적용
- 검증된 Team B 실제 신호만 읽기
- Spring의 주문 전 판정, Kill Switch, 잔고·주문 가능 금액 확인
- KIS 모의투자 지정가 주문
- 체결·미체결·잔고 대사

단순한 `cron 09:00`은 쓰지 않습니다. 휴장일, 대체공휴일, 장 운영시간 변경과 container 재시작을
처리할 수 있도록 XKRX session과 저장된 실행 원장을 기준으로 판단해야 합니다.

## 자동 모의투자 필수 안전장치

- 기본 상태는 비활성이고 앱 재시작 후 자동으로 활성화되지 않음
- Owner가 명시적으로 활성화·비활성화
- KIS 모의투자 계좌만 허용하고 실계좌 origin/TR ID는 allowlist에 없음
- 첫 단계는 종목·전략별 하루 최대 1건처럼 작은 상한
- 지정가, 수량, 가격, 총액과 거래시간을 서버가 다시 검증
- Kill Switch가 켜지면 새 주문 즉시 차단
- idempotency key와 거래일별 실행 원장으로 중복 주문 차단
- 주문·취소 write retry 0
- 응답이 불명확하면 재주문하지 않고 `PENDING_RECONCILIATION`으로 저장
- scheduler가 죽거나 재시작돼도 같은 session 주문을 반복하지 않음
- 모든 자동 주문은 Signal, 원칙, Risk 결과와 source hash를 감사 기록에 연결
- 자동 매도·손실 복구·물타기 로직을 임의로 추가하지 않음

아래가 모두 끝난 뒤 별도 OpenAPI 변경과 PR로 구현합니다.

2. Team B 결과의 Signal/모델 평가/백테스트 적재 경로 완료
3. Team A 주문 검토·제출·조회·취소 화면과 27개 API E2E 완료
4. KIS 모의투자 수동 인증 PASS
5. 자동매매 설정·활성 상태·실행 이력 API 확정
6. session clock, 중복 방지, Kill Switch, 상한, 대사 계약 확정
7. 장외시간·휴장일·재시작·부분체결·timeout을 fake transport로 검증
8. 24시간 service soak와 여러 XKRX session 시뮬레이션 통과

## 현재 수동 KIS 모의투자 인증

Owner만 다음 순서로 실행합니다.

```bash
./capstone up
./capstone mock configure
./capstone mock doctor

# XKRX 거래일 09:10~15:00 KST
./capstone mock certify --symbol 005930 --quantity 1
```

`mock doctor`는 자격증명 형식만 검사합니다. `mock certify`는 현재가 1회, 주문 전 잔고, 주문 가능 금액,
삼성전자 1주 지정가 매수, 즉시 전량취소, 체결, 주문 후 잔고, 미체결 대사를 수행합니다. token은 cache
상태에 따라 0회 또는 1회입니다. write retry는 0입니다.

체결·부분체결·취소 실패가 발생하면 자동 매도나 재주문을 하지 않습니다. 즉시 실패로 끝내고 KIS
모의투자 화면에서 주문과 잔고를 직접 확인합니다.

## 인증 결과 파일의 현재 보호

`up --mock`은 다음을 다시 검증합니다.

- 인증 요청과 결과 파일이 owner 전용 0600 일반 파일이고 canonical JSON인지
- 결과의 `inputSha256`이 인증 요청 bytes의 실제 SHA-256과 같은지
- 요청 commit과 결과 commit이 같은지
- PASS, 물리 호출 수와 timestamp 형식이 정확한지
- 현재 작업 폴더가 clean인지
- 인증 commit의 Git tree와 현재 HEAD의 Git tree가 완전히 같은지

따라서 PR commit에서 인증한 뒤 같은 파일 tree로 main에 병합된 경우는 허용하지만, commit 이후 파일을
하나라도 바꾸면 거부합니다. 인증 실행 시에는 Ed25519 승인, 5분 TTL과 single-use claim을 별도로
검증합니다. 인증 결과는 source tree 인증이므로 임의 시간 만료 대신 source가 바뀌는 즉시 무효가 됩니다.
이 보호는 KIS 모의투자 adapter를 여는 조건일 뿐 자동매매 권한을 만들지 않습니다.

## 외부 서비스 확장 원칙

새 KIS·ECOS 조회를 추가할 때는 operation, endpoint, 전송 필드, 최대 호출 수, credential mode,
TTL, retry와 비용 상한을 먼저 고정합니다. offline fixture와 parser를 검증한 뒤 별도 승인 범위에서만
실행합니다. 자동매매 scheduler가 데이터 provider를 무제한 polling하게 만들지 않습니다.

## 계속 유지할 경계

- KIS 실계좌 주문·정정·취소: 항상 비활성
- LightGBM: 연구·재현 전용, 주문 근거로 사용하지 않음
- RAG·뉴스·LLM 답변: Signal, RiskDecision, 주문 권한 없음
- SearXNG: 검색 fallback일 뿐 주문·신호 권한 없음
