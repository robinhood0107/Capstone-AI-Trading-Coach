## Async 구조

domain row, `async_job`, `event_outbox` insert는 하나의 PostgreSQL transaction이다. commit 이후 DB
dispatcher 또는 Kafka publisher가 처리한다. Kafka send와 `published_at` update는 별도 단계이므로
at-least-once이며 exactly-once로 표현하지 않는다.

```text
DB transaction
  └─ domain + async_job + event_outbox
       ├─ adapter=db    → Spring dispatcher → loopback authenticated Python gRPC
       └─ adapter=kafka → Kafka publisher  → Python consumer
                                      └─ processed_event + materialization + completion outbox
```

두 adapter는 같은 transport-neutral Python handler를 사용한다. 같은 event ID와 같은 payload hash는
no-op replay이고, 같은 ID와 다른 hash는 poison conflict다. Python은 DB commit 뒤에만 Kafka offset을
ack한다. completion/DLQ를 먼저 Kafka로 직접 발행하지 않는다.

## Adapter와 운영 스위치

```text
docker compose --profile kafka ...  # 인프라 선택
ASYNC_ADAPTER=db|kafka              # Spring adapter 선택
ASYNC_POLLING_ENABLED=true|false    # poller 명시적 opt-in
ASYNC_WORKER_ENABLED=true|false     # DB worker transport 명시적 opt-in
```

애플리케이션 기본 adapter는 DB지만 polling과 worker는 환경에서 명시적으로 활성화해야 한다. repository의
`.env.example`은 로컬 통합 runtime을 위해 둘 다 true로 둔다. Kafka profile은 adapter를 바꾸지 않는다.
unknown adapter, Kafka readiness/config 실패, silent fallback, dual-active는 모두 거부된다.

전환 절차는 producer/consumer quiesce → RUNNING lease와 unacked 작업 확인 → 정확히 한 adapter로
재기동이다. Kafka에서 DB로 돌아갈 때도 같다.

## DB queue와 상태 전이

- claim: `FOR UPDATE SKIP LOCKED`, stable order, outbox page 100
- poll interval: 고정 5초
- scheduler: 단일 thread, DB-time ShedLock
- claim transaction: claim만 수행하고 Kafka/file/RAG/RPC 작업은 하지 않음
- outbox lease: 30초
- async job lease: 5분, heartbeat 30초, hard deadline 15분
- physical attempt: 최대 3회, retry delay 1초/5초

```text
Outbox: PENDING → PUBLISHED
        PENDING/FAILED → FAILED → retry
        PENDING/FAILED → DLQ_REQUESTED

Job:   REQUESTED → RUNNING → COMPLETED
        REQUESTED/RUNNING → FAILED
        FAILED → RUNNING | NEEDS_REVIEW
```

stale claim token의 complete/fail은 conflict다. replay는 기존 row를 되돌리지 않고 새 ID와 `replayOf`를
만드는 append-only operation이다.

## 데이터와 권한 경계

- DB payload 최대 32 KiB, Kafka envelope 최대 64 KiB
- JSON depth 8, key 64, array 32, string 2,048 UTF-8 bytes
- error는 stable code/class 최대 128 bytes
- raw URL/path/provider body/header/credential/account/자연인 정보/자유서술 오류 금지
- DB SemVer와 Kafka integer schema version은 exact event registry로만 매핑
- unknown/legacy/poison event는 outbound 0으로 격리

`decision_app`과 `decision_worker`는 base-table broad DML/SELECT를 받지 않는다. secure-search-path
`SECURITY DEFINER` capability만 실행하며 PUBLIC execute는 revoke된다. worker의 Principle, order,
users, Flyway history, raw provider/RAG 접근은 SQLSTATE `42501`이다.

Admin status/replay는 JWT claim만 사용하지 않고 DB의 current `ACTIVE`, `ADMIN`, `securityVersion`을
재검증한다. raw payload/error/requester는 응답하지 않으며 cross-owner 조회는 append-only audit에 남는다.

## Kafka 로컬 경계

KRaft compose는 container `INTERNAL`, host `127.0.0.1` listener와 controller listener를 분리한다.
auto topic creation은 false이고 one-shot initializer가 catalog의 base/retry/DLQ topic을 정확히 만든다.
partition 3, local replication factor 1, 일반/retry retention 7일, DLQ retention 30일이다.

producer는 `acks=all`, idempotence true를 사용한다. broker success 후 별도 DB transaction으로 outbox를
PUBLISHED 처리하므로 update 실패 시 duplicate publish가 가능하고 consumer 멱등성이 이를 흡수한다.
partition key는 목적별 HMAC digest다.

Kafka UI는 별도 profile, loopback bind, login-form credential이 필수다. non-loopback/deploy는 TLS,
service identity, topic/group ACL이 모두 준비되지 않으면 시작하지 않는다.

## Failure matrix와 replay

DB suite는 duplicate claim, lease expiry/reclaim, stale token, worker commit 뒤 Spring update 실패,
artifact duplicate, stale/poison event, Admin drift, replay mismatch/dry-run, base/Flyway/append-only negative
privilege를 검증한다. Kafka suite는 publish-update 실패, duplicate materialization, commit 전/ack 전 crash,
rebalance duplicate, schema DLQ, retry 소진, payload/header/key/DLQ secret·account·PII 0을 검증한다.

replay CLI는 public REST가 아니다. dry-run이 기본이고 exact ID 최대 100, expected count, bounded reason,
5분 signed packet, 실행 직전 current Admin DB 검증을 요구한다. actor는 Admin audit에만 남고 Kafka에는
포함하지 않는다.

## S1.4와 미래 교체

현재 production은 Python/NumPy 11함수이고 runtime hot-swap 구조가 아니다. S1.4X Scala/Haskell은
production import/API/RiskEngine과 분리된 연구 runner다. 현행 Scala CLI SSOT는 `1.15.0`이다.

미래 교체는 별도 migration ADR 이후에만 branch-by-abstraction으로 진행한다: frozen contract로
`NumericAnalyticsPort` 정의 → Python을 유일 production adapter로 감쌈 → candidate를 offline shadow에서
비교 → exact error/`-0.0`/NaN·Inf/tolerance/security/same-host benchmark 통과 → 명시적 수동 activation.
shadow 결과는 Risk/API/order에 쓰지 않고 Python rollback pointer를 유지한다.

## 외부 blocker

실제 Return Engine artifact가 도착하기 전에는 real ingest, 독립 지표 재계산, 허용오차 표, 실제 성과,
P1 전체 완료를 주장하지 않는다. 다음 단계는 [P1 실물 artifact 잔여 체크리스트](P1_실물_artifact_잔여_체크리스트.md)를
따른다. S8.4는 kit만 준비됐고 참가자 모집·응답·IRB/면제 판단은 수행하지 않았다.

provider/live/account/live-order physical call은 S7/S8 구현과 검증에서 0건이다.
