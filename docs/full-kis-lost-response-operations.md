# FULL KIS 주문 응답 유실 시 확인

KIS 주문 POST의 응답이 끊겨도 같은 주문을 다시 제출하지 않는다. 같은 세션의 KIS 주문 내역에서 제출 전에는 없던 주문이 종목, 방향, 수량, 지정가, 주문구분, 시각으로 유일하게 확인될 때만 원주문 참조를 복구해 체결 대사를 이어 간다. 주문 내역이 불완전하거나 여러 건이 일치하면 새 주문을 보류하고 사람에게 근거 확인을 요청한다.

운영 복구 시에는 KIS 주문·체결·잔고를 각각 확인하고, 로컬 주문과 자동운용 보유의 수량·계좌 범위·digest를 한 트랜잭션에서 대사한다. 재무장은 미해결 주문이 없고 관측 digest가 일치한 뒤에만 진행한다. 서비스 health만으로 체결·대사나 용량 검증을 완료한 것으로 보지 않는다.

브로커 gRPC의 실행 제한과 Spring Bean Validation 상한은 항상 같은 값으로 유지한다. 불일치는 컨테이너 시작을 막을 수 있으므로 candidate 검사에서 두 설정 경계를 함께 검증한다.

## 부가 기능 중단과 주문 대사

FULL에서는 RAG v2나 뉴스 보존 프로세스가 종료돼도 Spring, 자동운용, 브로커가 계속 실행됩니다. healthcheck 출력의 `RAG_V2=READY`는 RAG gRPC가 응답한다는 뜻입니다. `WORLD_NEWS_RETENTION=RUNNING`은 프로세스가 실행 중이라는 뜻이며 마지막 보존 작업의 결과는 `worldNewsRetention` 로그에서 확인합니다. `DEGRADED`가 나오면 해당 자식의 종료 로그를 확인하고 원인을 고친 뒤 점검 시간에 API 컨테이너를 재시작합니다. 자동운용 같은 필수 자식이 종료되면 supervisor가 다른 자식도 종료하고 Compose의 재시작 정책에 맡깁니다.

DB가 잠시 끊기면 Spring health가 실패할 수 있습니다. 시작 단계의 자동운용은 DB 연결 오류가 나면 권한 확인을 최대 세 번 다시 시도합니다. 실행 중인 FULL 자동운용은 다음 순회에서 무장한 owner 목록을 다시 조회합니다. 뉴스 보존 루프는 DB 연결 오류를 기록하고 다음 주기에 보존 작업을 다시 시도합니다.

저장된 `orderId`가 있으면 같은 주문을 대사하고 누적 체결량의 차이만 반영합니다. 제출 마감 뒤에는 대사를 계속하면서 이미 계획된 다음 주문의 평가와 제출을 막습니다. 재개 중 마지막 결정 시점에서 일시 장애가 재시도 한도까지 이어지면 완료 키를 남기지 않고 기존 owner 스케줄러에 재시도를 맡깁니다. 당일 15:20 KST까지의 DB 재개 조건은 그대로 적용됩니다.

참조가 없는 `SUBMITTING`은 미확정으로 남기고 owner 정지 경로를 따릅니다. `AUTOMATION_CONTINUATION_RESUME`의 `RESUMING`, `RETRY`, `STOPPED`, `DONE`을 보고 재개 경과를 구분합니다. 특정 주문의 대사 완료는 실행 원장의 상태와 체결 기록으로 확인합니다.
