## 1. 한 문장 요약

> **Decision Platform이 이미 내린 판단을, 투자 경험이 적은 사람이 읽을 수 있는 화면으로 옮기는 층.**

여기서 중요한 단어는 **"이미 내린"** 입니다.
이 대시보드는 계산하지 않습니다. 판정하지 않습니다. 값을 추정하지 않습니다.
서버가 준 결과를 **왜곡 없이** 사람의 언어로 바꾸는 것이 전부입니다.

---

## 2. 이 화면이 하는 일과 하지 않는 일

| 한다 | 하지 않는다 |
|---|---|
| 서버가 준 `action`(ALLOW/WARN/HOLD/BLOCK)을 표시 | 판정을 직접 계산 |
| 서버가 준 `viewState`(READY/EMPTY/STALE)를 표시 | 신선도를 다시 판정 |
| 모델 성과를 나란히 배치 | 모델 학습·추론 |
| 백테스트 결과를 차트로 그림 | 백테스트 실행 |
| RAG 답변과 출처를 표시 | 답변 생성, 문장 편집 |
| 없는 값을 "없다"고 표시 | 없는 값을 추정하거나 0으로 채움 |

### 왜 이렇게까지 좁게 잡았나

자동매매 시스템에서 화면이 값을 만들어내기 시작하면, **어디까지가 서버의 판단이고 어디부터가 화면의 각색인지** 아무도 모르게 됩니다.

예를 들어 서버가 "VaR 값 없음"을 내려줬는데 화면이 `0.0%`로 그리면, 사용자는 위험이 0이라고 읽습니다. 이건 버그가 아니라 **거짓말**입니다.

그래서 이 프로젝트는 화면 계층에 딱 하나의 규칙을 세웠습니다.

> **서버가 말하지 않은 것은 화면도 말하지 않는다.**

이 문서에 나오는 거의 모든 설계 결정은 이 한 줄에서 파생됩니다.

## 3. 구조 — 네 겹으로 나눈 이유

```
┌─────────────────────────────────────────────┐
│  화면 (features/*/View.tsx)                  │  ← 사람이 보는 것
├─────────────────────────────────────────────┤
│  ViewModel (features/*/viewModel.ts)         │  ← 서버 응답 → 화면용 모양
├─────────────────────────────────────────────┤
│  API 계층 (shared/api/)                      │  ← 계약, 인증, 오류
├─────────────────────────────────────────────┤
│  Spring Decision Platform (외부)             │  ← 진짜 판단이 일어나는 곳
└─────────────────────────────────────────────┘
```

### 겹마다의 책임

| 겹 | 아는 것 | 모르는 것 |
|---|---|---|
| 화면 | ViewModel의 모양 | HTTP, 인증, endpoint 주소 |
| ViewModel | 서버 계약, 도메인 의미 | React, CSS, 화면 배치 |
| API 계층 | HTTP, 헤더, 오류 코드 | 도메인 의미, 화면 |

### 이 분리가 실제로 값을 한 순간

초안에서는 도메인 endpoint(`/decisions/{id}`)를 직접 부르고 프론트에서 ViewModel을 조립했습니다.
실제 계약을 확인해 보니 서버가 이미 `/dashboard/risk-results/{id}`로 ViewModel을 완성해서 주고 있었습니다.

**바꾼 파일: `endpoints.ts`, `wire.ts`, 각 `viewModel.ts`**
**손대지 않은 파일: 모든 `View.tsx`**

계층을 나누지 않았다면 화면 코드를 전부 다시 썼어야 합니다.

## 4. 데이터가 흐르는 길

### 주문 검토 화면을 예로

```
사용자가 dec_... 입력
      │
      ▼
IdInput ─── 정규식 검사 ──✗──▶ 빨간 테두리 + 안내 (요청 안 보냄)
      │ ✓
      ▼
useResource(enabled=true)
      │
      ▼
loadRiskResultView(decisionId)
      │
      ├─▶ GET /dashboard/risk-results/{id}   ← 권위 소스 (필수)
      │
      └─▶ GET /decisions/{id}                ← 상세 보강 (실패해도 진행)
      │
      ▼
fromDashboard() ─── viewState를 그대로 옮김
      │
      ▼
ViewState<RiskResultView>
      │
      ▼
AsyncBoundary ─── loading / empty / error / stale / ready 분기
      │
      ▼
화면
```

### 두 소스를 합친 이유

`/dashboard/risk-results/{id}` 는 안전하게 정제된 요약만 줍니다 — `reasons`, `principles`, `riskItems`가 전부 문장입니다.

`/decisions/{id}` 는 원본 수치를 줍니다 — 어떤 규칙이 얼마를 넘었는지, 위반·이슈·경고·기권이 각각 몇 건인지.

**요약만 있으면** 사용자가 "왜?"를 알 수 없고, **상세만 있으면** 서버가 정제한 안전한 표현을 버리게 됩니다. 둘 다 씁니다.

단, 우선순위가 있습니다.

> 판정(`action`)은 **항상 dashboard 쪽**을 씁니다.
> 상세 조회가 실패해도 화면은 뜨고, "상세를 못 불러왔다"고 알립니다.

## 5. 표현 방식 — 무엇을 어떻게 그렸나

### 5.1 전체 인상

목표는 **"조용한 금융 서비스"** 입니다. 화려하지 않고, 밀도가 높고, 캡처했을 때 보고서에 그대로 들어가는 화면.

| 요소 | 선택 | 이유 |
|---|---|---|
| 배경 | 차가운 회녹색 종이(`#EEF0EC`) | 순백은 눈이 아프고, 크림색은 금융 문서처럼 안 보임 |
| 모서리 | 거의 각짐(2px) | 둥근 카드는 소비자 앱 느낌. 이건 계기판에 가까움 |
| 그림자 | 없음 | 선(border)으로만 구분. 정보 밀도를 유지하기 위해 |
| 숫자 | 고정폭 + `tabular-nums` | 표에서 자릿수가 세로로 정렬되어야 비교가 가능 |
| 강조색 | 최소 | 색이 의미를 가져야 해서, 장식에 색을 쓰지 않음 |

### 5.2 색은 판정에만 쓴다

색 네 개가 **오직 판정 등급**만을 나타냅니다.

| 등급 | 색 | 값 | 뜻 |
|---|---|---|---|
| ALLOW | 깊은 초록 | `#16653F` | 통과 |
| WARN | 황토 | `#9A6510` | 진행 가능, 확인 필요 |
| HOLD | **회청색** | `#43505F` | 판단 보류 |
| BLOCK | 진한 빨강 | `#96262B` | 차단 |

**HOLD를 빨강이 아니라 회색 계열로 한 것이 의도적인 선택입니다.**

HOLD는 오류가 아닙니다. "필수 근거가 없어서 지금은 판단하지 않겠다"는 **정상적인 업무 결과**입니다. 빨강으로 칠하면 사용자가 시스템 고장으로 오해합니다.

### 5.3 판정 레일 — 이 화면의 서명

주문 검토 화면 맨 위에 가로로 네 칸이 놓입니다.

```
┌──────────┬──────────┬──────────┬──────────┐
│  ALLOW   │  WARN    │  HOLD    │ ■BLOCK■  │
│  허용     │  경고     │  보류     │  차단     │
└──────────┴──────────┴──────────┴──────────┘
  우선순위 낮음 ──────────────────────▶ 높음
```

현재 판정만 색이 칠해집니다.

**왜 이렇게 만들었나:** 명세서에 `BLOCK > HOLD > WARN > ALLOW` 라는 우선순위 규칙이 있습니다. 이 규칙을 글로 설명하면 읽지 않습니다. 왼쪽에서 오른쪽으로 갈수록 강해지는 막대로 그리면, 사용자가 **화면 구조에서 규칙을 읽습니다.**

"경고도 있고 차단도 있는데 왜 차단이 최종이지?"라는 질문이 이 그림 앞에서는 생기지 않습니다.

### 5.4 빗금 슬롯 — 없는 값의 시각 언어

값이 없을 때 이렇게 표시합니다.

```
┌─────────────┐
│░░근거 없음░░│   ← 45도 사선 빗금, 회색
└─────────────┘
```

`0`도 아니고, `-`도 아니고, 빈칸도 아닙니다.

**세 가지를 동시에 전달합니다.**
1. 여기에 값이 들어올 **자리가 있다**
2. 지금은 **근거가 없다**
3. 이건 **오류가 아니다** (오류는 빨간 상자로 따로 표시)

마우스를 올리면 왜 없는지 이유가 뜹니다.

이 표현은 세 곳에서 재사용됩니다.
- 지표 카드 (VaR, CVaR, 시장 국면)
- 표 셀 (ABSTAIN 모델의 성과 칸)
- 히트맵 (데이터 없는 달)

**구현:** `src/shared/ui/Numeric.tsx` 한 곳. `value: number | null`을 받아서 `null`이면 빗금을 그립니다. 화면 코드는 `null` 처리를 신경 쓸 필요가 없습니다.

### 5.5 ABSTAIN 칩 — 색을 주지 않는 표시

모델이 판단을 내지 못한 상태입니다.

```
┌──────────────┐
│░░ ABSTAIN ░░│   ← 무채색, 빗금
└──────────────┘
```

**ABSTAIN에 색을 주지 않은 이유:** ABSTAIN은 판정이 아닙니다. 모델이 "근거가 없다"고 말한 상태일 뿐입니다.

판정 색 네 개와 섞이면 사용자가 ABSTAIN을 다섯 번째 판정으로 오해합니다. 실제로 `ABSTAIN ≠ HOLD` 는 명세서가 명시적으로 구분하라고 요구한 항목입니다.

### 5.6 패널 머리표(eyebrow) — 계약 이름을 화면에 적는다

모든 패널 위에 작은 고정폭 대문자가 붙습니다.

```
DASHBOARD-RISK-RESULT.V1
이 주문을 내도 되는지
```

장식이 아닙니다. 이 패널이 **어떤 계약을 소비하는지** 적은 것입니다.

**왜:** 팀이 세 workspace로 나뉘어 있고, 화면과 백엔드를 다른 사람이 만듭니다. 버그가 났을 때 "주문 검토 화면 이상해요"보다 "`dashboard-risk-result.v1`이 이상해요"가 훨씬 빨리 해결됩니다.

발표할 때도 "이 화면은 이 계약을 씁니다"를 따로 설명할 필요가 없습니다.

### 5.7 사유를 네 칸으로 쪼갠 배치

주문 검토 화면 중간에 네 개의 열이 나란히 놓입니다.

| 원칙 위반 | 필수 근거 없음 | 경고 | 평가하지 않음 |
|---|---|---|---|
| 빨강 상단선 | 회청 상단선 | 황토 상단선 | 회색 상단선 |
| 기준을 실제로 넘음 | HOLD를 만듦 | 확인 필요 | 비교를 건너뜀 |

**섞으면 안 되는 이유:** 서버 계약에서 `violations`, `issues`, `warnings`, `abstentions`는 각각 다른 의미를 갖습니다.

특히 `abstentions`(평가하지 않음)를 위반 목록에 섞으면, 사용자는 자기가 규칙을 4개 어겼다고 읽습니다. 실제로는 2개를 어기고 2개는 그냥 평가 대상이 아니었을 뿐인데요.

각 열 아래에 "이게 무슨 뜻인지" 한 줄 설명을 넣었습니다. 특히 마지막 열에는 **"위반이 아닙니다"** 라고 명시했습니다.

### 5.8 언어 — 용어를 먼저 풀어서 쓴다

대상 사용자가 투자 경험이 적은 대학생입니다.

| 안 쓰는 표현 | 쓰는 표현 |
|---|---|
| `max_daily_orders` 위반 | 하루 최대 주문 횟수 기준을 넘었습니다 |
| `evidenceRequirement: REQUIRED` | 근거 필수 |
| `DATA_STALE` | 필요한 데이터가 오래돼 사용할 수 없습니다 |
| `citationCoverage: 1.0` | 출처 연결률 100% |
| MDD | 최대 낙폭 (MDD) — 고점 대비 하락폭 |

원래 코드값은 **작은 회색 글씨로 아래에 함께** 둡니다. 개발자가 로그와 대조할 수 있어야 하기 때문입니다.

원칙 설정 화면에서는 각 규칙마다 **"이 값을 어떻게 읽어야 하는지"** 한 줄을 붙였습니다.

> 하루 최대 주문 횟수
> 과매매를 막기 위한 하루 주문 건수 상한

## 6. 화면별 설계 의도

### `/` 현황

**질문:** "지금 내 상태가 어떤가, 자동주문은 켜져 있나?"

8칸 격자로 핵심 값만 보여줍니다. 그중 절반이 `근거 없음`으로 뜨는 게 정상입니다 — VaR, CVaR, 시장 국면을 만드는 단계가 아직 운영에 없습니다.

**이걸 숨기지 않은 이유:** 없는 기능을 화면에서 지우면, 나중에 생겼을 때 사용자가 새 기능인 줄 압니다. 자리를 남겨 두고 "아직 없다"고 표시하는 편이 정직합니다.

### `/principles` 내 원칙

**질문:** "내 기준을 어떻게 정하나?"

- 위: preset 3개 (보수형/균형형/공격형) — 카드를 누르면 아래 값이 한꺼번에 바뀜
- 아래: 규칙 8개를 슬라이더와 숫자 입력으로 조정

**자연어 입력을 만들지 않았습니다.** "손실 나면 좀 조심스럽게" 같은 문장은 판정 엔진이 쓸 수 없습니다. 구조화된 값만 저장합니다.

**저장 실패 시 자동 재시도를 하지 않습니다.** 409(버전 충돌)가 오면 "다른 곳에서 먼저 바뀌었으니 다시 불러온 뒤 직접 정하라"고 안내합니다. 원칙은 금융 판단의 기준이라, 화면이 마음대로 다시 보내면 안 됩니다.

### `/order-review` 주문 검토 ★ 핵심

**질문:** "이 주문을 내도 되나? 왜?"

3층 구조입니다.

1. **판정 레일** — 결론
2. **서버 요약** — 서버가 정제한 문장
3. **근거 상세** — 4열 분리 + 위반 수치 표 + 사용된 값 목록

위에서 아래로 갈수록 자세해집니다. 바쁜 사람은 1층만 보고, 따지고 싶은 사람은 3층까지 봅니다.

맨 아래 `semanticInputHash` / `snapshotArtifactHash` 앞 16자를 표시합니다. **판정 재현성 검증용**입니다. 사용자는 안 보지만, 나중에 "이 판정이 정말 그때 그 입력으로 나온 게 맞나"를 확인할 때 씁니다.

### `/model-evaluation` 모델 비교

**질문:** "세 모델이 뭐라고 하나?"

두 개의 축이 있고, **일부러 합치지 않았습니다.**

| 축 | 조회 키 | 뜻 |
|---|---|---|
| 성과 | `runId` | 이 실행에서 각 모델의 CAGR/MDD/Sharpe |
| 현재 신호 | `symbol` | 지금 이 종목에 대한 각 모델의 의견 |

`runId`는 학습·평가 실행 단위이고 `symbol`은 현재 시점입니다. 한 표에 넣으면 "이 종목의 Sharpe"처럼 읽히는데, 그런 값은 존재하지 않습니다.

**불일치는 표시만 합니다.** 모델 의견이 갈려도 주문 가능 여부는 바뀌지 않습니다. HMM은 예측 모델이 아니라 시장 국면 분류라서 불일치 계산에서 제외합니다.

### `/backtest` 백테스트 리포트

**질문:** "원칙을 켜면 뭐가 달라지나?"

이 화면의 목적은 **수익률 자랑이 아닙니다.**

지표 카드 4개 중 3개가 개선율이고, 마지막 하나가 **"수익률 대가"** 입니다.

> 수익률 대가
> 안전장치를 켜면서 포기한 연환산 수익률입니다.
> 개선만 보지 않고 대가도 함께 봅니다.

개선만 보여주면 광고가 됩니다. 대가를 같은 크기로 나란히 두는 것이 이 화면의 태도입니다.

Sharpe 비교 아래에는 **"구간이 겹치면 우열을 단정하지 않습니다"** 라는 문구가 고정으로 들어갑니다.

### `/rag` 금융 가이드

**질문:** "이 용어가 뭔가?"

**거부가 기능입니다.**

| 질문 유형 | 응답 |
|---|---|
| 개념 질문 | 설명 + 출처 |
| "지금 사도 되나요?" | `BLOCKED_ADVICE` — 거부 |
| "내 잔고 알려줘" | `BLOCKED_SENSITIVE` — 거부 |
| 근거 부족 | `RETRIEVAL_ONLY` — 출처만 |

거부 상태를 **숨기지 않고 그대로 화면에 띄웁니다.** 상태 코드도 함께 보여줍니다. 사용자가 "왜 답을 안 해주지?"가 아니라 "이건 답 안 하는 기능이구나"를 알게 하기 위해서입니다.

출처 연결률은 **답변이 생성됐을 때만** 표시합니다. 문장이 없으면 연결률은 의미가 없으므로 `0%`가 아니라 `근거 없음`으로 둡니다.

### `/report` 보고서 캡처

**질문:** "보고서에 넣을 그림을 어디서 따나?"

보고서의 그림·표 번호와 화면 위치를 1:1로 연결한 표를 놓고, 그 아래에 실제 화면을 캡처하기 좋은 배치로 다시 깝니다.

합성 데이터일 때는 **"보고서에 성과로 인용하지 마세요"** 경고가 표 바로 아래에 붙습니다.

## 7. 상태 모델 — 네 가지를 절대 섞지 않는다

모든 데이터 영역이 다섯 상태 중 하나입니다.

```typescript
type ViewState<T> =
  | { kind: 'loading' }
  | { kind: 'empty';  title, detail }
  | { kind: 'error';  code, message, retryable, requestId }
  | { kind: 'stale';  data, asOf, detail }
  | { kind: 'ready';  data, asOf }
```

### 화면에서 어떻게 다르게 보이나

| 상태 | 모양 | 사용자가 읽는 것 |
|---|---|---|
| loading | 회색 막대 3줄 | 기다리는 중 |
| **empty** | **점선 테두리 + 회색** | 자료가 아직 없음 |
| **error** | **빨간 실선 + 빨간 배경** | 불러오다 실패함 |
| stale | 황토색 왼쪽 선 + 데이터 표시 | 값은 있지만 오래됨 |
| ready | 그냥 데이터 | 정상 |

**empty와 error를 다르게 그리는 것이 핵심입니다.**

"백테스트가 아직 없다"와 "백테스트를 불러오다 실패했다"는 사용자가 취할 행동이 완전히 다릅니다. 전자는 백테스트를 돌려야 하고, 후자는 다시 시도하거나 서버를 확인해야 합니다.

같은 회색 상자로 보여주면 사용자는 구분할 방법이 없습니다.

### stale의 특이점

값을 **버리지 않습니다.** 데이터를 그대로 보여주되 위에 경고 띠를 답니다.

오래된 값도 참고는 됩니다. 다만 주문을 낼 수 있는지는 이 화면이 아니라 Decision API의 판정을 따릅니다.

### 서버 판정을 그대로 옮기는 부분

Dashboard endpoint는 `viewState`를 서버가 이미 정해서 줍니다.

```typescript
fromDashboard(envelope, map, emptyCopy)
```

이 함수는 `READY / EMPTY / STALE`을 **다시 계산하지 않고 그대로 매핑**합니다.

일반 endpoint(`/risk/portfolio` 등)만 `withFreshness()`로 프론트가 신선도를 판정합니다.

## 8. 오류를 다루는 방식

### HTTP 상태 코드로 분기하지 않는다

```typescript
// 이렇게 하지 않음
if (response.status === 404) { ... }

// 이렇게 함
if (error.code === 'NOT_FOUND') { ... }
```

서버 계약이 그렇게 정해져 있습니다. 같은 404라도 `NOT_FOUND`일 수도 `DECISION_EXPIRED`일 수도 있습니다.

### 오류 코드 22종에 한국어를 붙였다

서버 메시지는 영어입니다. 사용자에게 그대로 보여주지 않습니다.

```typescript
DATA_STALE: '필요한 데이터가 오래돼 사용할 수 없습니다.'
CONFLICT:   '다른 변경과 충돌했습니다. 최신 상태를 다시 불러오세요.'
```

`ApiFailure` 객체가 `userMessage`(한국어)와 `message`(원본)를 둘 다 갖습니다.

### 재시도 버튼을 아무 데나 달지 않는다

일시적 장애로 분류된 코드만 "다시 조회" 버튼이 나옵니다.

| 재시도 버튼 있음 | 없음 |
|---|---|
| `RISK_UNAVAILABLE` | `VALIDATION_ERROR` |
| `PYTHON_SERVICE_UNAVAILABLE` | `FORBIDDEN` |
| `DATA_STALE` | `NOT_FOUND` |
| `RATE_LIMITED` | `IDEMPOTENCY_CONFLICT` |

**금융 write는 절대 재시도 목록에 넣지 않았습니다.** 같은 주문이 두 번 나갈 수 있습니다.

### requestId를 화면에 표시한다

오류 상자 안에 작은 글씨로 `requestId fe.a3f9...`가 붙습니다.

사용자에게는 의미 없는 글자지만, 이걸 캡처해서 개발자에게 주면 서버 로그에서 정확히 그 요청을 찾을 수 있습니다.

### 요청 전에 미리 거른다

ID 형식은 서버가 정규식으로 검사합니다. 화면도 **같은 정규식**을 갖고 있습니다.

```typescript
decisionId: /^dec_[A-Za-z0-9_-]{8,96}$/
runId:      /^(run|demo)_[A-Za-z0-9_-]{8,96}$/
answerId:   /^rag_[A-Za-z0-9_-]{12,96}$/
symbol:     /^[0-9]{6}$/
```

형식이 틀리면 요청을 보내지 않고 입력 칸을 빨갛게 만듭니다. 서버에 갔다 와서 400을 받는 것보다 빠르고, 왜 틀렸는지도 알려줄 수 있습니다.

## 9. 안전과 보안

### 토큰을 저장하지 않는다

```typescript
// shared/api/session.ts
const state = { token: null, expiresAt: null, user: null };
```

그냥 **자바스크립트 변수**입니다.

- `localStorage` 안 씀
- `sessionStorage` 안 씀
- 쿠키 안 씀
- URL에 안 넣음

**새로고침하면 로그아웃됩니다.** 불편하지만 의도된 동작입니다. 토큰이 브라우저에 남아 있으면 다른 스크립트가 훔칠 수 있습니다.

### CORS 허용 헤더를 정확히 맞췄다

서버가 허용하는 요청 헤더는 네 개뿐입니다.

```
Authorization, Content-Type, X-Request-Id, X-Idempotency-Key
```

초안에서 `X-Client-Timezone`을 보내고 있었습니다. **이대로 붙였으면 모든 요청이 preflight 단계에서 막혔을 겁니다.** 계약을 읽고 제거했습니다.

### 멱등성 키를 붙이는 곳

부작용이 있는 요청에만 `X-Idempotency-Key`를 답니다.

- `POST /rag/ask`
- `POST /decisions/evaluate-order`

읽기 요청에는 붙이지 않습니다.

### 외부 링크

```typescript
safeExternalUrl(url)  // https가 아니면 null
```

`https`가 아닌 링크는 아예 렌더하지 않고, 렌더할 때는 `rel="noopener noreferrer"`를 강제합니다.

### HTML을 직접 그리지 않는다

`dangerouslySetInnerHTML`을 **한 번도 쓰지 않았습니다.** RAG 답변도 순수 텍스트로만 렌더합니다.

### 보안 헤더

`next.config.mjs`에서 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`를 설정합니다.

## 10. mock 모드의 설계

백엔드 없이 화면을 검증하는 모드입니다. 여기에도 원칙이 있습니다.

### 지름길을 만들지 않았다

mock 응답도 **같은 envelope**를 통과합니다.

```typescript
{ success, requestId, data, warnings, error }
```

mock 전용 우회 경로를 만들면 live로 바꾸는 순간 화면이 깨집니다.

### 서버 제약을 그대로 흉내낸다

| 제약 | mock에서도 재현 |
|---|---|
| Dashboard endpoint에 query 붙이면 거부 | ✓ `VALIDATION_ERROR` |
| ID 정규식 불일치 | ✓ `VALIDATION_ERROR` |
| 없는 ID | ✓ `NOT_FOUND` |
| `expectedVersion` 불일치 | ✓ `CONFLICT` |
| 응답 지연 | ✓ 240ms |

### fixture가 계약을 검증한다

`fixtures.ts`가 실제 스키마 타입을 import합니다.

```typescript
export const riskPortfolio: PortfolioRisk = { ... }
```

계약이 바뀌면 **fixture에서 타입 에러가 먼저 납니다.** 화면을 실행해 보기 전에 컴파일 단계에서 잡힙니다.

### 합성 데이터임을 계속 알린다

mock 모드에서는 화면 맨 위에 노란 띠가 항상 떠 있습니다.

> 합성 fixture — 화면 검증용 합성 데이터입니다. 보고서에 성과로 인용할 수 없습니다.

live 모드에서도 `fixtureClass`가 `SYNTHETIC_FAKE_E2E`면 같은 경고가 백테스트 화면에 붙습니다.

## 12. 고칠 때 알아야 할 것

### 백엔드 계약이 바뀌었을 때

1. `src/shared/api/wire.ts` 에서 타입 수정
2. `npx tsc --noEmit` 실행
3. 에러 난 곳을 따라가며 수정

타입이 연결돼 있어서 **컴파일러가 고칠 곳을 전부 알려줍니다.** 직접 찾아다닐 필요가 없습니다.

### 새 endpoint를 붙일 때

1. `wire.ts` 에 응답 타입 추가
2. `endpoints.ts` 에 함수 추가
3. `mock/transport.ts` 에 mock 경로 추가 (안 하면 mock 모드에서 404)
4. feature 폴더에 `viewModel.ts` 작성
5. View 작성

### 새 화면을 추가할 때

1. `src/features/<이름>/` 폴더 생성
2. `viewModel.ts` + `<이름>View.tsx`
3. `src/app/<경로>/page.tsx` 생성
4. `src/shared/ui/NavRail.tsx` 의 `ITEMS` 배열에 항목 추가

### 색이나 글꼴을 바꿀 때

`tailwind.config.ts` 한 곳만 고치면 전체에 반영됩니다.
화면 파일에 색 값(`#RRGGBB`)을 직접 쓰지 마세요 — 차트 색만 예외입니다(Recharts가 CSS 변수를 못 받음).

### 절대 하면 안 되는 것

| 금지 | 이유 |
|---|---|
| `null`을 `0`으로 바꿔서 표시 | 없는 값을 있다고 말하는 것 |
| 화면에서 판정 등급을 다시 계산 | 서버 판정과 어긋나면 재현 불가 |
| `localStorage`에 토큰 저장 | 보안 규칙 위반 |
| `dangerouslySetInnerHTML` 사용 | XSS |
| write 요청 자동 재시도 | 중복 주문 |
| `violations`와 `abstentions`를 한 목록에 | 의미가 다름 |
| 합성 데이터 경고 배너 제거 | 가짜 숫자가 성과로 인용됨 |

## 13. 일부러 만들지 않은 것

빈 화면으로 남겨 둔 것들입니다. 값을 지어내지 않기 위해서입니다.

| 항목 | 이유 | 화면에서 |
|---|---|---|
| 신호 시계열 그래프 | 이력 조회 API 없음 | 모델 비교의 타임라인이 empty |
| 최초 원칙 생성 | `POST /principles` 미연결 | "아직 만든 원칙이 없습니다" |
| Kill Switch 토글 | 위험한 조작이라 별도 검토 필요 | 상태 표시만 |
| 주문 제출 | 화면의 책임 밖 | `canSubmitOrder`만 표시 |
| 학습일지 | Journal 계약이 아직 없음 | 메뉴에 없음 |
| 종목별 리스크 | 해당 endpoint 미구현 | 없음 |
| 자동 스크린샷 | 범위 밖 | 캡처 체크리스트로 대체 |

**빈 화면도 설계입니다.** "아직 없다"고 정직하게 표시하는 편이, 그럴듯한 가짜 값을 채우는 것보다 낫습니다.
